Review request: sandboxed execution stack (wasm -> C via w2c2 -> tcc -> seccomp strict).

Repository: this directory. Read NOTES.md first for context and the threat model.

Trust boundary (please focus here, in this order):
1. host/main.c — x86_64 Linux, no libc, enters SECCOMP_MODE_STRICT then runs the guest. Imports env.read/env.write/env.exit.
2. rt/w2c2_base.h — rewritten runtime header for w2c2-generated C: software bounds checks on every memory access, static memory arena, memory.grow, table checks.
3. libc/ — the wasm32 guest libc (untrusted from the host's point of view, but part of the measured TCB).
4. build/w2c2/guest.c is an example of w2c2-generated code (large); build/rot13/guest.c a small one.

Goal of the sandbox: after prctl(PR_SET_SECCOMP, SECCOMP_MODE_STRICT), the process must only be able to read stdin, write stdout/stderr, and exit. Guest code is C generated by w2c2 from arbitrary (possibly malicious) wasm and compiled with tcc.

Questions:
- Can guest code (via the generated C + this header) read or write host memory outside the arena, or call an arbitrary address? Look for integer overflow in bounds checks, missing checks (bulk memory, data segments, tables), and anything in the generated code shape that bypasses the header's checked accessors.
- Is anything the host does after prctl a syscall other than read/write/exit/sigreturn (including implicit ones tcc might emit)?
- Are there correctness bugs in the libc printf/qsort/realloc/FILE layer that could make w2c2 output differ between platforms (nondeterminism)?
- Anything that makes the measured TCB larger than needed without adding safety.

Please be concrete: file:line, the failure scenario, and a suggested fix. Do not modify files. Write your findings as a markdown report to stdout.
